\chapter{Software Architecture Design}
\label{ch:software-architecture-design}

\noindent
This chapter presents the software architecture that supports reproducible EEG experimentation in this project. It describes a layered architecture, the main execution flow, the AI processing pipeline, and the key data schemas used to make runs traceable and repeatable.
\vspace{1em}

\section{Software Architecture}
\label{sec:software-architecture}

The system is designed using a \textbf{layered client–server architecture}, consisting of a React-based frontend and a FastAPI backend. The backend is implemented as a modular monolith, where functionalities are organized into domain-specific modules such as API handling, data processing, visualization, and machine learning.
\vspace{0.5em}

At its core, the system follows a \textbf{pipeline-oriented architecture}, where EEG data is processed through sequential stages (e.g., preprocessing, epoch extraction, and feature generation). This structure enables reproducibility and flexible recomputation when parameters change.

\section{Domain Model}
\label{sec:domain-model}

The \textbf{domain model} of the system represents the key entities and their relationships involved in EEG data analysis and visualization. The platform is designed around a research-oriented workflow, supporting both \textbf{single-subject analysis} and \textbf{cohort-based analysis}.

\subsection*{Core Entities}
The primary domain entities are defined as follows:

\begin{itemize}
    \item \textbf{Subject}: Represents an individual participant in the dataset. Each subject contains multiple experimental tasks and associated EEG recordings.
    \item \textbf{Task}: Represents a specific experimental condition or recording session associated with a subject. Each task serves as the entry point for EEG data processing.
    \item \textbf{EEG Raw Data}: The original recorded EEG signals loaded from disk. This data is the starting point of the processing pipeline.
    \item \textbf{Processed Signals}: Intermediate representations of EEG data, including:
    \begin{itemize}
        \item \textbf{Filtered Signals}: Signals after applying frequency filtering and noise removal.
        \item \textbf{Cleaned Signals}: Signals after artifact removal and preprocessing.
    \end{itemize}
    \item \textbf{Epochs}: Segmented EEG data derived from raw signals based on event markers. Epochs enable time-locked analysis of brain responses.
    \item \textbf{Evoked Responses}: Averaged EEG signals across epochs, representing stimulus-locked neural activity.
    \item \textbf{Cohort}: A dynamically defined group of subjects selected using filtering criteria (e.g., task type, demographic attributes). Cohorts enable batch analysis across multiple subjects.
    \item \textbf{Model}: Represents machine learning models used for training and evaluation. Models consume processed EEG features derived from epochs or evoked data.
    \item \textbf{Visualization Output}: The final output of the system, which can be either:
    \begin{itemize}
        \item \textbf{Graphical plots} (e.g., time-domain, frequency-domain, topographic maps).
        \item \textbf{Tabular data} (e.g., EEG metadata, feature tables, training summaries).
    \end{itemize}
\end{itemize}

\subsection*{Relationships Between Entities}
The relationships between the entities are structured as follows:

\begin{itemize}
    \item A \textbf{Subject} contains multiple \textbf{Tasks}.
    \item A \textbf{Task} produces \textbf{EEG Raw Data}.
    \item \textbf{EEG Raw Data} is transformed into \textbf{Processed Signals} and \textbf{Epochs}.
    \item \textbf{Epochs} are further transformed into \textbf{Evoked Responses} and \textbf{Features} for \textbf{Model} training.
    \item A \textbf{Cohort} is a collection of multiple \textbf{Subjects}, each processed independently.
    \item \textbf{Visualization Output} is generated from any stage of the pipeline depending on user-selected actions.
\end{itemize}

\subsection*{Processing Flow}
The domain model follows a sequential processing pipeline:

\begin{center}
\textbf{Subject} $\rightarrow$ \textbf{Task} $\rightarrow$ \textbf{Raw Data} $\rightarrow$ \textbf{Signal Cleaning/Filtering} $\rightarrow$ \textbf{Epoching} $\rightarrow$ \textbf{Evoked/Features} $\rightarrow$ \textbf{Visualization} or \textbf{Model Training}
\end{center}

\section{Design Patterns}
\label{sec:design-patterns}

To ensure a modular and extensible architecture capable of handling high-throughput data, the following design patterns were implemented:
\vspace{0.5em}

\begin{itemize}[leftmargin=*]
    \item \textbf{Pipeline Pattern:} EEG processing workflow
    \item \textbf{Facade Pattern:} API endpoints
    \item \textbf{Strategy Pattern:} parameter-driven behavior
    \item \textbf{Factory Pattern:} model instantiation
    \item \textbf{Registry Pattern:} task preprocessor selection
    \item \textbf{Observer Pattern:} WebSocket progress updates
    \item \textbf{Repository Pattern:} structured EEG cache
    \item \textbf{Composite Pattern:} Pipeline Session is a combination of schemas
\end{itemize}

\section{Design Class Diagram}
\label{sec:design-class-diagram}

The system adopts a modular and layered design, where responsibilities are separated across execution, processing, visualization, and infrastructure components.

\noindent
\subsection*{Core Execution Components}
\begin{itemize}
    \item \textbf{TaskExecutor}: Handles the execution of the EEG processing pipeline for a single \textbf{Subject--Task} pair. It is responsible for:
    \begin{itemize}
        \item Loading raw EEG data.
        \item Applying preprocessing steps (filtering, cleaning).
        \item Generating \textbf{epochs} and \textbf{evoked responses}.
        \item Dispatching results to visualization or training modules.
    \end{itemize}
    \item \textbf{CohortExecutor}: Manages batch processing across multiple subjects. It maintains a collection of \textbf{TaskExecutor} instances and executes them iteratively. Additional validation and aggregation logic are applied at this level.
\end{itemize}

\noindent
\subsection*{Processing Pipeline Components}
\begin{itemize}
    \item \textbf{SignalCleaner}: Performs artifact removal and preprocessing on raw EEG signals.
    \item \textbf{SignalSpatial}: Handles spatial transformations and channel-level operations.
    \item \textbf{TaskLoader / TaskResolver / TaskProcessor}: These components collaboratively define and execute processing steps:
    \begin{itemize}
        \item \textbf{TaskLoader}: Loads task-specific configurations and data.
        \item \textbf{TaskResolver}: Determines the required processing steps based on user input.
        \item \textbf{TaskProcessor}: Executes the processing pipeline.
    \end{itemize}
    \item \textbf{TrainerDataBuilder}: Prepares processed EEG data for machine learning tasks.
\end{itemize}

\noindent
\subsection*{Visualization Components}
The visualization system is divided into three categories:
\begin{itemize}
    \item \textbf{Plot Modules (plot/)}: Generate single visualizations such as time-domain plots, frequency plots, and topographic maps.
    \item \textbf{Grid Plot Modules (grid\_plot/)}: Generate multi-condition visualizations for comparative analysis.
    \item \textbf{Data and AI Views (data/, ai/)}: Produce tabular outputs such as EEG summaries, metadata, and model training results.
\end{itemize}

Supporting components include:
\begin{itemize}
    \item \textbf{PlotMerger}: Combines multiple figures into a unified visualization.
    \item \textbf{PlotFinalizer}: Applies consistent styling and formatting across all plots.
\end{itemize}

\noindent
\subsection*{Schema Layer}
\begin{itemize}
    \item \textbf{Parameter Schemas}: Define input parameters for filtering, visualization, and training. These schemas serve both:
    \begin{itemize}
        \item \textbf{Request validation} (FastAPI layer).
        \item \textbf{UI rendering} (dynamic parameter generation).
    \end{itemize}
    \item \textbf{UI Schemas}: Define session state, task configuration, and view structure.
\end{itemize}

\noindent
\subsection*{Infrastructure Components}
\begin{itemize}
    \item \textbf{CacheManager}: Stores intermediate processing results (e.g., cleaned signals, filtered signals, epochs) using a hierarchical structure: \textbf{Subject} $\rightarrow$ \textbf{Task} $\rightarrow$ \textbf{Processing Stage} $\rightarrow$ \textbf{Parameter Hash}.
    \item \textbf{ParticipantsLoader}: Loads subject metadata and dataset structure.
    \item \textbf{ProgressLogger \& WebSocketManager}: Provide real-time feedback to the frontend during long-running operations.
\end{itemize}

\noindent
\subsection*{Interaction Flow}
\begin{enumerate}
    \item The user selects a mode (single or cohort) and defines parameters via \textbf{schemas}.
    \item The system initializes either a \textbf{TaskExecutor} or \textbf{CohortExecutor}.
    \item The execution layer processes EEG data through the pipeline.
    \item Intermediate results are \textbf{cached} to optimize repeated computations.
    \item The output is passed to \textbf{visualization modules} (plot/grid/data/ai).
    \item Final results are returned to the user interface.
\end{enumerate}

\noindent
\subsection*{Design Characteristics}
\begin{itemize}
    \item \textbf{Modularity}: Each component has a clearly defined responsibility.
    \item \textbf{Reusability}: Processing steps are reused across visualization and training workflows.
    \item \textbf{Scalability}: \textbf{CohortExecutor} enables batch processing across multiple subjects.
    \item \textbf{Extensibility}: New plots, filters, and models can be added without modifying core logic.
\end{itemize}

The \textbf{Visualization module} (app/plots) contains submodules for different types of outputs:
\vspace{0.5em}

The \textbf{AI Model module} (app/ai\_models) defines machine learning models used within the platform. These models can be trained and evaluated using processed datasets.
\vspace{0.5em}

Additionally, the system maintains a \textbf{job/output storage structure} (jobs/ai/train/...) that stores training results, logs, and model artifacts, along with the cache for each pipeline step in \textbf{eegcache} folder (such as prefiltered, cleaned, epochs, etc.) While not a full asynchronous job system, this structure supports persistence and traceability of preprocessing and model training runs.
\vspace{0.5em}

This modular design ensures separation of concerns, making the system maintainable, extensible, and aligned with the research workflow.

\section{Sequence Diagram}
\label{sec:sequence-diagram}

\subsection{Experiment Execution Flow}
\label{subsec:realtime-tracking-process}
\textbf{Scenario: Run an experiment}
\begin{enumerate}
    \item Select subjects/sessions and the CCD task.
    \item Load BIDS/HED events and construct CCD-ITI windows with aligned RT and correctness labels.
    \item Apply a fixed preprocessing configuration to the ITI epochs.
    \item Compute verification plots (e.g., SNR spectra) to confirm steady-state characteristics.
    \item Extract features and train models for RT regression and correctness classification.
    \item Evaluate using standard metrics and export a run summary (configs, metrics, and plots).
\end{enumerate}

\section{Pipeline}
\label{sec:pipeline}

\subsection{AI Processing Pipeline}
\label{subsec:ai-processing-pipeline}

The AI processing pipeline is designed to enforce traceability. Each stage consumes explicit inputs and produces versioned outputs:
\begin{enumerate}
    \item \textbf{Ingestion:} load CCD runs and parse events/metadata.\footnote{\cite{hbn_fair_2024}.}
    \item \textbf{Trial construction:} extract fixed-length ITI windows and attach labels.
    \item \textbf{Preprocessing:} filter, normalize, mitigate artifacts, and create epochs.
    \item \textbf{Verification:} compute SNR spectra and related plots for steady-state validation.
    \item \textbf{Features:} compute ITI-derived features (e.g., spectral power at stimulation frequencies/harmonics).
    \item \textbf{Modeling:} train RT regressors and correctness classifiers.
    \item \textbf{Evaluation:} compute metrics and export artifacts for reporting.
\end{enumerate}
